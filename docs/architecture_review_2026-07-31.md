# Architecture Deep Review — 2026-07-31

Read-only review of the tile-owner architecture on `feature/tile-owner-architecture`
(post bug-fix campaign, HEAD 73a6d39). Method: six independent deep-review agents
(durability/consistency, scheduling/ownership, resource coherence, redundancy/dead
paths, layering, HPC-claims-vs-code), 65 raw findings, every finding independently
adversarially verified; **48 confirmed, 17 refuted**. No code was edited.

## Verdict

**The streaming tile-owner core is sound.** All six reviewers independently
credited the main line: one coherent durable-truth hierarchy (slot snapshots as
payload truth -> fsync'd reducer progress manifests as ledger -> final chunk
artifacts as product -> SQLite as honestly-rebuildable cache), correct crash
ordering in the commit sequence, idempotent folds with loud partial-overlap
failure, worker-count-invariant streaming checkpoint identity, and genuinely
coherent VRAM management (single headroom function feeding pool cap, reservation
ledger, and slab tiler, with no hold-and-wait).

The confirmed problems cluster in three belts:

1. **Edges of the newest mechanisms** — the dead-owner rescue protects the drain
   loop but not the flush/inspect/finalize barriers after it (a worker death
   there still hangs the driver forever); opportunistic startup recovery can
   publish a PARTIAL non-partitioned chunk as COMMITTED (silent amplitude loss
   in the non-streaming local path); snapshot payload renames are not fsync'd
   though the manifest referencing them is; the async snapshot writer is gated
   to RAM-mode accumulators — which the hkl40-class workload that motivated it
   never uses (its accumulators are file-mode), so the mechanism cannot fire on
   its own justifying case.

2. **Non-reference deployments** — the dask-jobqueue "slurm" backend emits SGE
   directives into SBATCH scripts (workers cannot launch at all) and silently
   drops the GPU directive; the heap-trim plugin and worker env are never
   registered on job-queue backends; driver-side memory backpressure is
   unreachable in EVERY default deployment (it keys off memory_limit>0, which
   the architecture deliberately sets to 0); worker-count divisors assume the
   cuda-local layout and are wrong under the shipped MPI layout. The one-node
   cuda-local path is battle-tested; the multi-node paths are validated only as
   far as the cluster sim exercised them (case-per-node + one mpirun case).

3. **Three coexisting architecture generations** — legacy pair execution and
   stage2_replacement are config-dead (no example, notebook, launcher, or SLURM
   script can reach them) yet carry a full parallel scheduler and commit flow;
   durable_shared generation checkpoints survive only for a non-streaming
   distributed default the code's own comments call pre-tile-owner; plus dead
   modules, guard-alive dead branches, two parallel durable stage-1 payload
   formats, and assorted duplicated helpers.

Cross-cutting: `run_residual_field_stage` is a single ~1,420-line function with
10+ state-sharing closures (every new mechanism lands as another closure);
`core/storage` imports upward into residual_field/decoding; and several
identity-bearing knobs (subchunk slot count, shard grid budget, intervals-per-
shard, lattice-FFT switch) live OUTSIDE the parameter digest — changing one
silently DELETES the checkpoint family instead of namespacing a new one.

**Bottom line**: correct-by-construction where it matters most (the streaming
hot path and its durability chain), with real but fixable resilience gaps at
the barrier seams, a broken never-exercised jobqueue backend, and roughly a
third of the residual/scattering surface serving architectures this design has
already replaced. Nothing found challenges the numerical results produced so
far.

## Refuted findings (survived adversarial review of the review)

Seventeen claims were killed by verification — including several plausible ones
(e.g. "streaming stage-commit consumers break publish_run" — the compatibility
artifacts are written directly at finalize; "ManifestOnlyDatabaseManager is a
dead path" — it is coherent, load-bearing duplication). See list at the end.

## Dimension summaries

### durability

The streaming durable-truth chain is, in its main line, genuinely coherent and mostly well-ordered: durable slot snapshots are the payload truth, the fsync'd reducer progress manifest is the ledger (rebuilt paths at discovery, so the ledger itself is relocation-safe), final chunk HDF5 artifacts are the product, SQLite is honestly rebuildable (one-transaction overlay + COMMITTED-progress credits), and the commit sequence (savez -> rename -> chunk-mutex manifest union -> mark-committed -> SQLite -> unlink previous seq) is correctly ordered for process crashes. Several subtle pieces deserve explicit credit as SOUND: the interval-set fold ledger makes work-unit retries idempotent and fails loudly on partial overlap (local_accumulator.py:643-665); the async writer's captured-set-only durable marking (local_accumulator.py:774-793) and the drain->lock->recheck loop in flush (backend.py:2226-2260) close the real seq-collision races; and streaming finalize's family validation derives coverage from snapshot FILE metadata, not the manifest, so lost-update/split-brain scenarios become loud failures instead of corruption (backend.py:339-452, 601-712). However, the chain has one serious hole outside streaming: opportunistic startup recovery publishes PARTIAL owner-level (non-partitioned) snapshot families as COMMITTED, deletes the snapshots, and the completion run then overwrites the chunk artifact with only the newly computed intervals — silent amplitude loss (the partitioned/streaming deferral does not cover the non-partitioned branch, which has no coverage check at all). On leanness: there are demonstrably TWO parallel durability universes. The attempt/candidate/chunk-commit/stage-commit machinery is unreachable from the residual stage itself (owner-local reduction is force-enabled by raises), fed only by scattering non-streaming and stage2_replacement, yet execution.py and tasks.py still carry its full residual-side plumbing as dead branches; and the durable_shared_restartable generation-checkpoint universe survives only for the non-streaming distributed case that the code's own comments describe as predating the tile-owner design. Streaming runs also write none of the stage-commit manifests that publish_run and the manifest-based decoder source require — those consumers are mode-disjoint by construction, which is coherent but worth stating: for streaming runs the compatibility artifacts ARE written directly at finalize and the decoder uses the loose-file identity resolver.

### scheduling

The core invariants of the tile-owner residual stage are sound, and several mechanisms the prompt flagged as suspicious compose correctly: fold idempotence holds under at-least-once execution (interval-set dedup with loud partial-overlap failure at local_accumulator.py:600-665, restore-from-durable-snapshot on owner remap at backend.py:1329-1338, cross-slot duplicates rejected at finalize backend.py:378-385); a unit can never be rescued while its early flush is in flight because target_remaining only reaches zero when every unit of the target is terminal, and a dead-owner early-flush future is detected and resubmitted at the barrier (execution.py:853-875); deferred infra resubmits cannot leak past the drain loop because its condition includes them (execution.py:2413); owner death after task completion but before snapshot fail-stops at coverage validation rather than corrupting; and a driver crash between finalize and the SQLite mark is healed by the manifest-driven cache rebuild (SQLite is genuinely just a cache). The real defects are at the seams of newer mechanisms: (1) dead-owner rescue ends exactly where the highest-exposure pinned-future phase begins - the flush/inspect/finalize barriers block forever on a worker death that the drain loop would have rescued (high); (2) the per-(chunk,slot) owner spread degenerates to chunk-only placement whenever worker count divides chunk count (hkl40's 4x4 exactly), silently re-creating the low-prefetch starvation the slot interleave claims to fix (medium, currently masked by prefetch 8). On leanness: the non-owner-local path is fully dead code kept alive by its own removal-guard raises (~200+ lines plus the attempt-commit imports) - the non-streaming owner-local path, by contrast, is still real; SLOT content-addressing no longer earns its complexity now that co-location is explicitly obsolete and could be a rank-mod-slots assignment, but only behind a snapshot-layout version bump since slot id is checkpoint address; and the four recovery ledgers are mostly cleanly partitioned by failure class, with two narrow overlaps (dask x driver retries in cpu policy; worker-killing tasks enjoying the largest budget while bypassing the breaker).

### resources

VRAM management is the strong half of this design and is genuinely coherent: one absolute headroom function (`_headroom_bytes_for_total`) feeds the pool cap, the reservation ledger and the slab tiler; `_uncommitted_budget_growth_bytes` closes the "free VRAM can't see future pool growth" hole; `_ensure_plan_reservation` drops its claim before waiting so concurrent transforms cannot hold-and-wait; and sizing/reserving share one footprint model. `cpu_resources.py` is the right shape (min over SLURM/affinity/cgroup/host; cgroup-aware memory), and the shard grid budget is a host-independent constant so checkpoint identity survives machine changes. Host RAM is the weak half, and structurally so: there is no closed loop at all. Dask's per-worker RSS limiter is deliberately 0 everywhere (cuda-local, threads-local, mpi), which silently disables the driver-side backpressure controller because that controller keys off `memory_limit > 0`; the worker trim plugin's host-pressure branch is unreachable at its own default (`MOSAIC_HEAP_TRIM_EVERY=1`); and the plugin is never registered at all on job-queue backends. What remains is a single a-priori admission test whose divisor (`_expected_worker_count`) uses visible-GPU count as a proxy for "processes sharing this host's RAM" — correct only for the cuda-local reference layout and wrong in the MPI layout the repo itself ships. Alongside sit two vestigial mechanisms (the async snapshot writer is gated to exactly the storage mode its motivating workload never uses; the lattice cache is the largest RAM consumer and the only one with no release path) and several shadowed or co-linear knobs. Nothing here threatens numerical correctness; the risks are OOM kills and silent ~10x slowdowns.

### redundancy

The hot path (streaming tile-owner + lattice type-2) is lean and its safety nets (type-3 fallback for near-lattice geometry, finufft/direct-DFT CPU fallbacks for CPU-only laptops, per-interval HDF5 artifacts for the default non-streaming mode that all 347 example configs including 1D/2D/chemical use) are genuinely load-bearing and should stay. Around it, however, the architecture carries three full generations of stage-2 execution (legacy pair, replacement, streaming/default residual engine) of which two are reachable only via env/config switches no example, notebook, launcher, or SLURM script sets; a durable_shared generation-checkpoint backend whose own selection comment admits it predates the tile-owner changes; several outright-dead modules and functions (core/scattering/persistence.py, compute_streamed_interval_tasks, load_existing_scattering_partial_result, execute_inverse_cunufft, the local-window inverse experiment); two parallel durable stage-1 payload formats (HDF5 interval artifacts vs the streaming npz store); in-repo inspect.signature feature-detection at 16+ sites; and a family of small copy-paste helpers (four budgeted-LRU caches, two prefetch-window pools, duplicate env parsers, worker-address and atomic-JSON helpers) plus two pre-tile-owner launcher scripts that encode the exact workarounds the new architecture removed.

### layering

The tile-owner design's durable-authority layering (attempt store -> commit -> stage commit, SQLite as rebuildable cache) maps onto modules better than the package graph first suggests — the module-level import graph is provably acyclic and the commit modules depend strictly downward — but three structural debts stand out. First, core/storage is not the leaf the project's own rule demands: run_state_cache.py imports the residual_field/scattering/decoding commit modules (run_state_cache.py:9-30), the exact violation for which cleanup.py and publisher.py were already relocated to core/workflow with shims (cleanup.py:1-10 states the rule); the fix is the same mechanical relocation. Second, residual_field/execution.py and backend.py are god-modules in the precise sense that new mechanisms (early flush, dead-owner rescue, infra backoff, async snapshots) accrete as closures and branches instead of components: run_residual_field_stage is one ~1,420-line function (execution.py:1151-2573) with 10+ state-sharing nested closures, and one 2,000-line backend class serves both reducer layouts — all separable by pure code motion. Third, the config story is ad hoc: ~101 MOSAIC_* env vars read at ~91 sites with knob-by-knob inverted precedence against the untyped runtime_info dict (both orderings appear within resolve_residual_field_reducer_backend itself, backend.py:2969-2986), and two identity-affecting knobs (shard grid budget, intervals-per-shard) live outside every digest and manifest — guarded against corruption by _invalidate_incompatible_local_checkpoints (execution.py:611) but a real hole in the authority hierarchy for resume semantics. The ~25 genuine lazy imports are cycle-phobia rather than cycle-breaking (every one verified hoistable; only the CUDA-adapter deferrals are justified), and the cross-package private imports (workflow/stage2_replacement's 8 private names from two packages; the drifted duplicate _current_worker_addresses) mark seams extracted without promoting a public surface. Recommended moves, all behavior-preserving: relocate run_state_cache to workflow, split the two residual_field god-modules by code motion, and promote/relocate the stage2_replacement seam plus the two misplaced shared types (ScatteringIntervalArtifactPolicy, is_same_node_local_client) out of residual_field.

### hpc-claims

The streaming (tile-owner) core is largely portable as claimed: slot assignment is content-addressed and fixed at 8 (execution.py:376-390, streaming.py:85-95), shard packing is deterministic given the config (planning.py:131-192), owner/finalize maps are placement-only and never enter identity (execution.py:393-465), stage-1 store writes are atomic and idempotent (streaming.py:227-274), COMMITTED resume credits are chunk-granular so they cannot strand a partially-durable slot (run_state_cache.py:436-513), GPU admission is host-keyed rather than cluster-keyed (gpu_admission.py:186-194), and streaming SQLite marking is genuinely single-writer on the driver (execution.py:2520-2541, backend.py:1877-1881). The claims break down outside that core. (1) Worker-count invariance is real for streaming but not enforced: the slot count is client-kind-dependent (sync=1), and none of the identity-bearing knobs (slot count, shard grid budget, intervals-per-shard, lattice-FFT switch) are in the parameter digest that namespaces checkpoints, so a mismatch is resolved by DELETING the checkpoint family rather than by writing a separate one; the non-streaming owner-local path is outright worker-count dependent through the adaptive partition plan. (2) Shared-FS safety hinges on a best-effort flock whose failure is silently swallowed, while the FS capability probe hardcodes file_lock_required=False and never probes locking; the per-chunk reducer-progress manifest is a read-modify-write single point of contention and is the sole source of the finalize snapshot family. (3) The mpi/slurm backends have real plumb-through defects: the job-queue path injects SGE directives into SLURM job scripts and clobbers the GPU directive, and "max_workers: auto" resolves to a hardcoded 4 for every non-cuda-local backend (which is why the cluster-sim multinode config has to hardcode 4). Also note serial_bottlenecks.md item 8 prescribes WAL while sqlite_connection.py:21 uses journal_mode=DELETE — DELETE is the correct choice for NFS, so the doc, not the code, is wrong there.
